# 사내 AI 플랫폼 담당자(플랫폼 PM 겸 아키텍트) 관점의 비평

## 한 줄 판정
보고서 품질 3.5/5. 아이디어 판정 **Conditional Go**. 상용·오픈소스 지형도와 "좌표는 파서에서, 인용은 문자열로 검증"이라는 설계 원칙은 그대로 쓸 수 있지만, 보고서는 개인 SaaS 전제 때문에 build/buy/OSS/wait 비교, 접근 권한, PPT 변환 충실도, 그리고 이미 GPT·Gemini를 쓰는 플랫폼에 가장 싸게 붙이는 경로를 다루지 않았다. 의뢰인 맥락에서는 "기존 RAG 위에 얇게 조립하는 자체 구축"이 맞고, 조건은 중복 업로드·버전 거버넌스와 문자열 검증 통과율 측정이다.

## A. 보고서 품질 평가

### 잘한 점
1. **L0–L4 다섯 단계 분류**가 모든 제품·프로젝트에 일관되게 적용되어 있어, 플랫폼 담당자가 "우리는 지금 L2이고 목표는 L3인가 L4인가"를 한 장으로 결정할 수 있다. 두 노트의 분류를 보고서가 그대로 보존했다.
2. **좌표 출처에 따른 아키텍처 구분**이 정확하다. RAGFlow는 "하이라이트를 LLM과 분리"(파서 좌표)하고 Kotaemon은 "LLM이 evidences 리스트를 돌려주지 못하면 하이라이트가 사라지며 Llama3.1-8B에서는 열 번에 한 번도 안 되게 나타났다"는 대비는, 모델을 GPT·Gemini로 바꿔 쓰는 플랫폼에 모델 비의존 설계가 필수임을 바로 알려준다.
3. **반증을 숨기지 않았다.** "하이라이트가 있으면 검증 시간이 62.4초에서 47.3초로 약 25% 줄고 ... 틀린 답을 틀렸다고 잡아내는 정확도는 72.2%에서 54.8%로 떨어졌다"는 인용은 사내 기능 기획서에 반드시 들어가야 하는 리스크다.
4. **운영 설계 처방이 구체적이다.** "PDF 변환, 두 해상도의 페이지 PNG, 파서 JSON, 정규화 영역을 인제스트 시 모두 만들어 정적 자산으로" 두고, 질의 시 `sources` 이벤트를 먼저 보내라는 것은 바로 백로그 티켓으로 옮길 수 있다.

### 논리 비약·과장·약한 근거
1. **"넷뿐"과 "확인된"의 과장.** 서두는 "원본 페이지 위에 하이라이트를 실제로 그리는 수준이 확인된 것은 Adobe, Hebbia, RAGFlow, Allganize 넷뿐"이라 하지만, 같은 보고서의 표는 Humata를 "L3–L4 (PDF), 원본 페이지 렌더 예", Kotaemon을 "L4 (텍스트 검색), 예"로 분류한다. Hebbia는 노트가 "vendor/marketing-adjacent sources; no independent hands-on"이라고 못 박은 사례인데 "확인된" 넷에 들어 있다. 숫자를 강하게 쓰려다 자기 표와 어긋났다.
2. **"기술 장벽은 낮다"와 "90%대 후반이 아니면 부채"의 긴장.** 서두는 "좌표를 돌려주는 파서와 문장 단위 인용을 돌려주는 API는 이미 상품화되어 있어 기술 장벽은 낮다"고 하고, 결론은 "그 숫자가 90%대 후반에 이르지 못하면 이 아이디어의 차별화 요소는 부채가 된다"고 한다. 둘 다 사실일 수 있지만, 플랫폼 담당자 입장에서 비용이 드는 곳은 부품이 아니라 접착 코드(청크→페이지·bbox 맵, 인용 문자열 정렬, 폴백 UX)다. 노트도 "No vendor offers (c) end-to-end in a chat API"라고 썼다. 보고서는 이 접착 공수를 어디에서도 추정하지 않는다.
3. **Microsoft 날짜를 하나로 고정.** 보고서는 "GA 2027년 2월로 잡혀 있으며 날짜가 반복해서 밀렸다"고만 쓴다. 노트는 "Conflicting dates elsewhere: Preview Oct CY2026 / GA Nov CY2026, or Preview Aug 2026"을 함께 적고 "treat as unshipped at GA level"로 정리했다. wait 결정에는 가장 이른 날짜도 필요하다. 더 중요한 것은 Deep citations가 "참조 문서의 해당 부분으로 직접 링크"하는 L3이고 PDF는 후순위이며 M365 Copilot 라이선스와 SharePoint 저장이 전제라는 점인데, 보고서는 이것이 자체 RAG 플랫폼의 대체재가 될 수 있는지 한 번도 묻지 않는다.
4. **Anthropic Citations 중심 처방.** "문장 단위 귀속: Anthropic Citations가 가장 정밀하고, 나머지는 사후 정렬이 필요하다"는 소제목은 Claude를 쓰지 않는 조직에는 벤더 추가를 뜻한다. 보고서는 OpenAI `file_citation`이 "파일 수준"이고 Gemini는 "응답 텍스트 쪽 오프셋"만 준다고 바르게 적었지만, 그렇다면 GPT·Gemini 사용자에게는 어떤 경로가 남는지(검색된 청크에 앵커 ID를 심고 모델이 ID를 인용하게 하는 Tensorlake식 패턴을 보고서 자신이 소개했다)를 결론으로 끌어오지 않는다.
5. **비용 모델이 개인 사용자 전제.** "월 300질문 사용자(문서 200개, 약 6,000쪽)" 기준 "저가 모델에서 월 약 0.43–0.45달러"는 B2C 마진 계산이다. 기업 플랫폼에서 하이라이트 기능의 한계 비용은 LLM이 아니라 업로드당 변환·래스터화·파싱이고, 직원 수만큼 같은 문서가 중복 업로드되면 이 비용이 그대로 곱해진다. 보고서는 "시각 우선 제품의 지배적 인제스트 비용은 LLM이 아니라 레이아웃 파싱"이라고 맞게 짚고도 중복이라는 변수를 넣지 않았다.
6. **PPT·Word 변환 충실도 공백.** HWP에 대해서는 "H2Orestart 변환 충실도를 측정한 공개 평가는 없으므로 ... 자체 테스트 세트가 필수"라고 쓰면서, 주류 포맷인 PPTX·DOCX의 LibreOffice 변환 충실도(폰트 치환, 겹친 텍스트 박스, SmartArt, 페이지 수 불일치)는 한 줄도 없다. 변환 PDF 위에 그린 하이라이트의 정확도는 변환 충실도의 하한을 넘지 못한다.

### 노트 대비 왜곡 또는 누락
배정된 두 노트(open_source_platforms.md, global_commercial_products.md)와 대조한 결과, 수치·인용·분류는 **대체로 일치**한다. RAGFlow `position_int` 구조, Issue #18148/#18149의 overlap 좌표 버그, Kotaemon `render.py`의 PDF 게이트, Open WebUI PR #25076 미머지, Glean "Navigating directly to the cited page ... isn't supported", Claude Citations의 스캔 PDF 인용 불가, Gemini File Search `page_number`, Open WebUI 브랜딩 조항은 노트와 동일하게 옮겨졌다. 다음은 어긋나거나 빠진 것이다.

- **경미한 과장**: 위 1번(Hebbia를 "확인된" 넷에 포함)과 3번(MS 날짜 단일화).
- **누락 1 — 뷰어 컴포넌트만 이식하는 선택지.** 노트는 "Forking RAGFlow's `document-preview` + `react-pdf-highlighter` wiring and its `position_int` schema is licence-clean (Apache-2.0) and is the fastest way to study a working L4 implementation"이라고 추론했다. 보고서는 RAGFlow를 플랫폼 단위로만 다루고 이 옵션을 떨어뜨렸다. 기존 RAG가 있는 조직에는 가장 중요한 선택지다.
- **누락 2 — Open WebUI `display_file`의 슬라이드 점프.** 노트는 0.11.1 `display_file`이 "PDF/Word/slide deck at a page or slide number"를 열고 0.11.2는 Word·슬라이드를 "as the finished document"로 미리보기한다고 적었다. 보고서는 "Glean만 '프레젠테이션의 특정 슬라이드로 점프'를 언급"이라고 써서 OSS에도 슬라이드 단위 L3 선례가 있다는 사실을 지웠다.
- **누락 3 — Gemini File Search의 제약.** 노트는 "cannot combine with Google Search grounding or URL context in the same request"를 적었다. 보고서의 P1 "웹 근거와 문서 근거의 통합 모델"을 Gemini 한 호출로 구현할 수 없다는 뜻인데 빠졌다.
- **누락 4 — RAGFlow Go 재작성의 운영 함의.** 노트는 "forking the highlight pipeline now means forking Go code as well as the legacy Python path"라고 했다. 보고서는 재작성 사실만 쓰고 포크 비용은 쓰지 않았다.
- **누락 5 — Office 뷰어 서버.** 노트는 OnlyOffice(AGPLv3)·Collabora(MPL-2.0)를 "full editor servers, not annotation canvases"로 분류했다. 보고서는 아예 언급하지 않는다. 결론은 같지만 기업 담당자가 가장 먼저 물을 선택지이므로 "왜 아닌가"가 한 줄 필요했다.

### 빠진 관점
- **접근 권한.** 원본 페이지 이미지와 호버용 크롭 PNG는 새로운 자산 표면이다. 원본 문서의 ACL을 상속하는 서명 URL, 캐시 금지, 채팅 로그에 저장되는 `cited_text`(문서 내용 그 자체)의 보존 기간이 필요하다. 보고서의 프라이버시 절은 "Google의 업로드 학습 여부" 같은 B2C 걱정만 다룬다.
- **기존 플랫폼과의 통합 경로.** 색인을 다시 만들어야 하는가(아니다. 기존 청크를 변환 PDF 위에서 `search_for()`로 정렬하면 재색인 없이 L3가 된다), 벤더 벡터 스토어를 쓰고 있다면 어디가 막히는가(OpenAI file_search는 파일 수준이라 막힌다), 모델을 바꿔도 깨지지 않는가 같은 질문이 없다.
- **의사결정 표.** 지형도는 풍부하지만 build/buy/OSS/wait를 한 표로 비교한 곳이 없다. D 섹션에서 보충한다.

## B. 아이디어 평가 (의뢰인 실제 맥락 기준)

### 이 관점에서 보는 핵심 가치와 핵심 위험
핵심 가치는 보고서가 "사원이 결국 원본을 다시 여는 행동은 바로 '맞는 문서, 틀린 구절'과 '근거 없는 인용'이라는 두 실패가 보이지 않기 때문"이라고 쓴 대목에 있다. 의뢰인의 증상이 정확히 이것이다. 매장 직원이 원본을 다시 여는 시간은 측정 가능한 비용이고, 답변 옆의 페이지 이미지가 그 시간을 줄이는지도 측정 가능하다. 추가로, 의뢰인 맥락에서만 두드러지는 가치가 하나 있다. 정책 PPT의 슬라이드 하단 "2026.09 개정" 같은 버전 표식은 청킹 과정에서 버려지는데, 원본 페이지를 이미지로 띄우면 그 표식이 눈에 들어온다. 텍스트 스니펫(L2)은 이것을 절대 보여주지 못한다.

핵심 위험은 셋이다. 첫째, 보고서가 경고한 **거짓 안심**이다(HoT 54.8%). 둘째, 보고서가 다루지 않은 **변환 충실도**다. 주류가 PPT·Word이므로 LibreOffice 변환 PDF 위에 그리게 되는데, Linux에 맑은 고딕이 없으면 글꼴 치환으로 줄바꿈이 밀리고 슬라이드 수가 바뀔 수 있다. 셋째, 역시 보고서가 다루지 않은 **중복·버전 문제**다. 같은 정책 자료를 여러 직원이 따로 올리면 "정확한 하이라이트가 오래된 문서를 가리키는" 상황이 생기고, 보고서의 문자열 검증 계약은 이 실패를 잡지 못한다(문자열은 그 문서 안에 실제로 있으므로 검증을 통과한다).

### 보고서 결론 중 유지할 것 / 바꿔야 할 것
유지할 것.
- "하이라이트는 검증됐을 때만 그린다"는 계약과, 실패 시 "하이라이트 없이 페이지만 열면서 그 사실을 말해야 한다"는 폴백 명시.
- 좌표는 파서(가장 작은 단위)에 저장하고 인용은 사후 정렬한다는 설계. 모델을 GPT와 Gemini 사이에서 바꿔도 하이라이트가 유지된다.
- 인제스트 시 선계산, 질의 시 `sources` 선발송, 프롬프트 캐싱.
- 문장별 grounded / model-knowledge 상태 구분과 장식용 인용 금지.

바꿔야 할 것.
- **"한국어 파싱(HWP·스캔) 우선 투자"는 폐기.** 의뢰인의 문서는 본사가 만든 born-digital PPT·Word·PDF다. 보고서가 최대 리스크로 꼽은 HWP 변환 충실도와 스캔 OCR은 이 맥락에서 거의 사라지고, 그 자리에 PPTX·DOCX 변환 충실도가 들어온다.
- **"검증 도구 포지셔닝"은 "원본 재열람 시간 단축 기능"으로.** 시장 포지셔닝이 아니라 사내 지표의 문제다. 성공 지표는 보고서의 인용 정밀도에 더해 "답변 후 원본 파일 열기 비율"과 "하이라이트 클릭 후 원본 열기 비율"의 차이여야 한다.
- **우선순위 재배열.** 보고서 P2의 "PPT 슬라이드 뷰"는 주류 포맷이므로 P0(변환 PDF 위에 그리되 슬라이드 번호로 표기), P1의 "소스 날짜·버전 배지"는 중복 업로드 구조 때문에 P0, P1의 "모바일 전폭 근거 시트"는 매장 단말이 모바일이라면 P0. 반대로 P1 "웹 검색 근거"는 사내 정책 질의에 불필요하므로 보류.
- **Anthropic Citations 전제 제거.** 검색된 청크마다 `<c id="p12-3">` 앵커를 넣고 모델이 앵커 ID를 인용하게 한 뒤 서버가 ID→{page, bbox}로 해석하는 모델 비의존 경로를 기본으로 한다. GPT·Gemini 어느 쪽이든 동일하게 동작하고 두 번째 LLM 호출이 필요 없다.

### 이 관점에서 권하는 첫 행동 (2주 안에)
1. **중복·버전 실태 측정(2일).** 업로드된 파일 전체의 SHA-256과 정규화 텍스트 해시를 뽑아 완전 중복 비율, 같은 파일명·다른 해시(버전 불일치 후보) 비율을 낸다. 이 숫자가 D 섹션 추천의 전제다.
2. **변환 충실도 샘플 테스트(3일).** 실제 정책 PPT·Word 20개를 unoserver(상주 LibreOffice)로 PDF 변환하고, 맑은 고딕·나눔·Noto CJK 폰트 설치 전후로 페이지 수 일치율과 눈으로 본 레이아웃 깨짐을 기록한다. 보고서가 HWP에 요구한 테스트를 PPT·Word에 적용하는 것이다.
3. **재색인 없는 L3 프로토타입(5일).** 기존 청크 텍스트를 변환 PDF 위에서 PyMuPDF `search_for()`로 찾아 페이지와 사각형을 얻고, 페이지 PNG에 사각형을 그려 답변 옆에 띄운다. 핵심 산출물은 UI가 아니라 **문자열 검증 통과율**(기존 청크가 변환 PDF에서 그대로 발견되는 비율)이다. 이 비율이 보고서가 말한 "90%대 후반"에 못 미치면 청커 또는 변환기를 먼저 고친다.
4. **원본 재열람 베이스라인(병행).** 플랫폼 로그에 "답변 후 N분 내 원본 다운로드/열기" 이벤트를 심어 현재 비율을 잰다. 기능 출시 후 비교할 유일한 지표다.

## C. 의뢰인에게 묻고 싶은 질문
1. 본사 스탭이 올린 정책 자료를 매장 직원이 보는 구조인가, 아니면 매장 직원도 각자 같은 파일을 다시 올리는가. 현재 접근 범위는 완전 개인 격리인가, 공유 폴더가 있는가. (이 답이 중복 비율, ACL 모델, 공식 코퍼스 도입 여부를 결정한다.)
2. RAG의 검색·청킹은 자체 구현(벡터 DB, 자체 청커)인가, OpenAI 벡터 스토어·Gemini File Search 같은 벤더 관리형인가. 청크 메타데이터에 파일 ID와 페이지 번호가 남아 있는가. GPT는 Azure OpenAI 경유인가(그렇다면 Azure Document Intelligence를 같은 계약 안에서 쓸 수 있다).
3. 매장 직원의 단말은 데스크톱 POS인가 모바일인가, 그리고 전체 업로드 중 HWP·스캔 PDF의 실제 비중은 얼마인가.

### 추천: Build(얇게 조립) + 컴포넌트 차용
이유는 네 가지다. 첫째, 노트가 결론 낸 대로 "No vendor offers (c) end-to-end" 즉 인용 텍스트를 페이지 위 좌표로 되돌리는 단계는 어차피 누구도 팔지 않으므로 buy·wait로 사라지지 않는다. 둘째, 의뢰인은 이미 인제스트·검색·채팅 UI를 갖고 있어 Build 공수의 절반 이상이 이미 지출되어 있다. 셋째, 보고서가 최대 리스크로 둔 HWP·스캔이 이 맥락에서는 주변부이고 born-digital PPT·Word·PDF는 로컬 파서(PyMuPDF)로 좌표가 나오므로 Upstage·Azure DI 같은 새 데이터 반출 계약 없이 시작할 수 있다. 넷째, wait의 두 후보는 모두 자체 플랫폼 밖에서 작동한다. Copilot Deep citations는 플랫폼을 M365로 옮기자는 제안이고, Gemini File Search는 검색을 Google에 맡기자는 제안이다. 둘 다 "하이라이트 기능 추가"가 아니라 "플랫폼 교체"다.

단계는 L3 먼저다. 변환 PDF의 해당 페이지 이미지를 답변 옆에 띄우고, 문자열 검증을 통과한 청크에만 구절 하이라이트를 올린다. 검증 실패 시 보고서의 처방대로 "이 답변의 근거 구절을 페이지 안에서 정확히 찍지 못해 페이지만 표시합니다"를 말한다. 뷰어는 자체 PNG+SVG 오버레이가 가장 단순하고 서버·클라이언트 좌표 불일치가 없다. PDF.js 기반 뷰어는 텍스트 선택·검색이 필요해질 때 붙인다.

보안·권한 측면의 조건은 셋이다. 페이지 PNG와 크롭 PNG는 원본 문서와 같은 ACL 검사를 거친 짧은 TTL 서명 URL로만 서빙하고 CDN 캐시를 금지한다. 채팅 로그에 저장되는 `cited_text`와 좌표는 문서 내용이므로 문서 삭제 시 함께 삭제되는 참조로 둔다. 파서를 외부 API(Upstage, Azure DI)로 확장할 때는 기존 GPT·Gemini 반출 심사와 같은 절차를 다시 밟는다.

### "직원 개별 업로드" 구조가 하이라이트 가치에 미치는 영향
이 구조는 하이라이트 기능의 비용을 곱하고 가치를 깎는다.

- **비용 곱셈.** 같은 200쪽 정책 자료를 50명이 올리면 변환·래스터·파싱이 50번 돌고 페이지 이미지가 50벌 저장된다. 바이트 해시로 완전 중복은 걸러지지만, PPT를 다시 내보내거나 한 슬라이드만 고친 사본은 해시가 달라 걸러지지 않는다. 변환 산출물을 파일 해시 키로 공유하는 캐시는 첫 주에 넣어야 하고, 그래도 근사 중복은 남는다.
- **"정확한 하이라이트, 틀린 문서."** 매장 A 직원은 9월 개정판, 매장 B 직원은 7월판을 올렸다면 둘 다 자기 문서 안에서는 완벽하게 검증된 하이라이트를 보고 서로 다른 답을 받는다. 보고서의 문자열 검증 계약은 문서 내부 일치만 보장하므로 이 실패를 통과시킨다. 보고서가 P1에 둔 "소스 날짜·버전 배지"와 "검색된 청크 간 숫자·날짜 모순 플래그"가 이 구조에서는 P0가 되는 이유다. 한 걸음 더 가면, 같은 정규화 텍스트 해시 군(같은 제목·다른 버전)을 묶어 "조직 내에 더 새로운 버전이 있습니다"를 근거 패널에 띄울 수 있다.
- **가치의 역설.** 역설적으로 원본 페이지 렌더링은 이 문제를 드러내는 데 가장 좋은 도구다. 슬라이드 하단의 개정일, 머리글의 문서 번호는 텍스트 청크에서는 사라지지만 페이지 이미지에는 남는다. 즉 이 구조에서 하이라이트의 가치는 "구절을 찍어 준다"보다 "어느 버전의 문서를 보고 답했는지를 직원이 1초 안에 알게 한다"에 더 가깝다.
- **구조적 처방.** 본사가 발행하는 "공식 정책 코퍼스"(버전 관리, 시행일 메타데이터, 지역·직무 그룹 ACL)와 개인 업로드를 분리하고, 답변은 공식 코퍼스를 우선 검색하며, 근거 패널에 "공식/개인" 배지를 단다. 이것은 하이라이트 기능이 아니라 거버넌스 변경이고, 현재의 개인 격리 권한 모델을 그룹 모델로 바꾸는 일이다. 하이라이트 기능이 이 변경을 강제하지는 않지만, 이 변경 없이는 하이라이트가 "각자 다른 문서의 정확한 근거"를 보여주는 데 그친다. 따라서 질문 C-1의 답이 "각자 다시 올린다"라면, 2주 안의 첫 행동에 코퍼스 분리 설계가 추가되어야 한다.
